# dip-desc-restyle — 卡池簡介重塑產線

工作目錄一律 `C:\Users\User\dip-vinyl-home\desc-restyle`。每批 50 張。

**預設一批走完全程再開下一批**——逐張審稿會把整批全文帶進上下文，堆越多後面每輪重送越貴。
店主可用第二個參數改成接力或全平行（見下節），但**不論哪種模式，
逐張人工審稿一次只做一批、做完就上線收尾**，不要累積多批的稿子最後一起處理。

## 參數解讀

**跑哪些批次**

- `059` 或 `059 060` → 跑指定批次。
- `3 批`、`三批` → 從下一個未跑批次起連跑 3 批。
- `150 張` → 換算成 3 批（每批 50 張）。
- 沒給參數 → 讀 `progress.json` 的 `status` 找出下一個未跑批次，跑 1 批，並在開工回報時說明跑的是哪一批。

**用什麼節奏跑**（第二個參數，**預設序列**）

| 參數 | 模式 | 說明 |
|---|---|---|
| （不給） | **序列** | 一批完整走完七步、上線收尾，才開下一批。店主 2026-08-02 的原始裁定。 |
| `接力`／`pipeline` | **接力** | **建議的平行法**。A 批進 hook 層時就開 B 批的研究層；**審稿與上線仍嚴格照批次順序、一次只做一批**。 |
| `平行`／`並行`／`parallel` | **全平行** | N 批的研究→hook→寫作全部同時跑完，最後才逐批審稿上線。**只在 N ≤ 3 時接受**。 |

### 選模式前必須向店主說明的代價

**代理階段平行沒有壞處**——子代理各有自己的上下文，五組研究平行跑不會讓主線變貴。
**真正的成本在主線**：

- **逐張審稿會把整批 50 張全文帶進主線上下文**（約 1.2 萬字／批）。序列模式下，A 批審完、上線、
  收尾之後那些文字就不再需要重送；全平行模式下三批的全文會同時壓在上下文裡，
  **後面每一輪對話都要重送**——這正是店主當初禁止平行的理由。
- **跨批更正會來不及傳遞**。序列模式下，A 批審稿查出的錯誤（例如「Reid Miles 1955 年底才加入 Blue Note」）
  能即時寫進 B 批的特注；平行模式下 B 批可能早已派工完畢，**只能事後回頭改稿或重推 KV**。
  歷史上這類跨批更正發生過（054 與 055 都宣稱疊錄「首度」，是在 055 審稿時才發現、回頭改了已上線的 054）。

**接力模式是折衷**：省下的是代理的等待時間（每批約 40–60 分鐘），付出的是「B 批研究層派工時，
A 批的審稿更正還沒出來」。因此**接力模式下 B 批的特注只能吃 A 批研究層與 hook 層的回報，
不能吃 A 批的審稿結果**——若 A 批審稿查出影響 B 批的事實，必須當場補進 B 批的 hook 或寫作層特注。

### 各模式的硬性護欄

- **不論哪種模式，逐張人工審稿一次只做一批，且做完就上線收尾**（更新 progress.json、補備忘錄、commit），
  不要累積三批的稿子最後一起處理。
- **上線順序必須照批次號**，因為後批的特注引用了前批的通論歸屬。
- 子代理上限 20。接力模式同時最多兩批在飛（最壞情況：B 批研究 5＋A 批 hook 或寫作 2＝7）；全平行三批的研究層是 15，仍在限內，
  **但不要讓三批的研究層與 hook 層同時在跑**。
- **跨批次的通論分配與同藝人排除條款，必須在派工前一次規劃好全部 N 批**（見「開工前」第 2 點的通論帳本），
  否則平行模式下無法互寫排除。

## 省流量裁定（2026-08-02 店主指示，現行預設）

**流量優先於速度。** 配置與理由：

- **研究層維持 5 組 Sonnet**——不是為速度，是中斷保險：歷史七次內容過濾器／額度中斷，
  中斷重跑燒掉的流量遠高於多養三個代理的固定開銷；研究層本來就是最貴的一層（WebSearch 結果吃 token），
  拆細是把單一代理的損失面壓小。
- **hook 層 2 組（a–c、d–e）、寫作層 2 組（前半／後半）**——每省一個子代理就省一份固定開銷
  （系統開場＋讀 base 檔＋派工詞＋完工回報＋回到主線的通知），一批合計省 6 份、以 063–065 實測估約一成多流量。
- **凡更正必逐 key 標明屬於哪張卡**（2 組配置下的更正路由全靠這條，見步驟 4）。
- **機器 QA 與逐張審稿一項不減**——QA 腳本在本機跑、不吃流量；審稿是品質底線。
- **接力模式照常可用**（省的是等待、不是流量）；**全平行最傷流量**（多批全文同時壓在主線上下文、每輪重送），非店主點名不用。
- 更激進的「hook 併入寫作層」可再省一整層，但會失去「寫作前攔掉 hook 前提錯誤」的閘門
  （歷史多次靠它擋下），**未採用**；店主若要再議。

## 派工詞怎麼寫（先看這節，能省一半輸出）

**下列內容已經寫在 `prompts/research-base.md`、`hook-base.md`、`writer-base.md` 裡，
派工詞不要再重打一遍**——三份 base 檔各層代理都會先讀：

- 廠牌規則（2026-08-02 的新裁定）、反向禁令兩分法、題材無禁區三限制
- 字元規則、字數區間、拉丁人名的字數陷阱
- 回報紀律（不得覆述原文）、不動 git／PROJECT_MEMORY、臨時檔前綴
- 研究層另含：**方法論**（特注是指派不是事實、請查證、明確回報推翻主線之處）
  與 **AI 生成百科站需交叉驗證**的警告

**派工詞只保留四樣**：①該組的卡單（key｜artist｜album 逐字）、②該組的逐張特注、
③該組要帶入的上一層更正、④輸出路徑與張數。每份因此少掉三、四百字。

**若某條規則變更**，改 base 檔、不要改派工詞——否則會兩邊打架。

## 派工方式（**最容易做錯的地方**）

**同一層的代理必須在同一則訊息裡一次全部派出**（多個 Agent 工具呼叫並排在一個回應裡），
背景執行。**研究層一次派 5 個；hook 層與寫作層各一次派 2 個**（2026-08-02 店主裁定省流量優先，見「省流量裁定」一節）。
**一個一個派會慢上數倍且毫無好處**——它們彼此不需要對方的產出。

**但層與層之間必須等齊**：五組研究**全部**回來、跑完 `qa-batch.mjs research` 之後才動 hook 層，
因為 hook 的特注要帶入研究層回報的所有更正；hook 全部回來、查完跨組撞頭之後才 merge 並派寫作層。

**平行的是「層內」，不是「批次之間」**——這兩件事別搞混：

| | 做法 |
|---|---|
| 同一層的代理 | **一次全部派出、平行跑**（不受模式影響） |
| 研究層 → hook 層 → 寫作層 | **等齊再進下一層**（不受模式影響） |
| 批次 A → 批次 B | **依模式**：序列＝A 上線後才開 B；接力＝A 進 hook 時開 B 的研究；全平行＝一起跑 |

子代理上限 20，一批研究 5＋hook 2＋寫作 2（合計 9 人次，同時在飛最多 5 個），額度充裕。

**等待期間不要每個代理回來就寫一段評論**——累積整層跑完再一次回報（見文末「回報紀律」）。

**w2-062 – w2-128 這 67 批的卡單已於 2026-08-02 一次規劃完畢、預先寫入
`batches/wave2/w2-0XX-cards.json`。直接讀該檔即可，`build-next-batches.mjs` 不要再跑**
（它會回報可分池 0 張；且它照 `restyle-tasks.json` 原順序切，會重現已經修掉的 713 組跨批藝人）。
配置的理由、規則與全表見 `BATCH_PLAN.md`。

- **批量不一定是 50**：w2-077 為 45、w2-112 為 43、w2-128 為 41 張。

  這幾批照常拆五組即可，只是每組 8–9 張。
- 卡池日後若新增專輯，新卡不在這 67 批內，需另行分批。

  060 的「廠牌共同創辦人把自己的鋼琴唱片放進自家目錄」兩張。）

    這兩批要在跨子組的特注互寫排除條款。

- **同家族連號的批要一次盤點通論帳本**：rock/pop 佔 w2-079–100 共 22 批、

**等五組研究全部回來、`qa-batch.mjs research` 跑完才動這一層。**

### 4. 合併＋寫作層 —— **2 組 × 約 25 張**，**model `opus`**，**一則訊息一次派出兩個**

**等 hook 全部回來、跨組撞頭查完才 merge。**

```bash
node merge-writer-input.mjs w2-0XX --split=2   # 省流量預設：二等分（writer-1＝前半、writer-2＝後半）
node merge-writer-input.mjs w2-0XX             # 五組切法保留給速度模式，店主明講要趕時才用
```


### 6. 逐張人工審稿（**最重要，不可省**）

把 50 張全文印出來逐張讀。**機器只驗「有沒有來源」，驗不出「來源對不對」**——
近六批靠人工審稿抓到的錯誤穩定落在每批 3–9 處，其中多數要現場上網查證。

高頻錯誤型態（依歷史頻率排序）：

1. **榜單年代錯置**——**1958 年 8 月以前的單曲一律不得寫 Billboard Hot 100**（該榜那時才創設）。
   已重演兩次（Chuck Berry、Julie London）。同理注意各榜的創設年。
2. **人物關係與時序**——「妻子」是當時就是，還是後來才結婚？（Abbey Lincoln 1962 才與 Roach 結婚、
   Julie London 1959 才與 Bobby Troup 結婚、〈Her〉題獻的 Goldie Getz 是 Stan Getz 的**母親**不是妻子。）
3. **hook 前提整個錯掉**——比單一事實更嚴重，要連 hook 重寫，並同步 research／hooks／input 三層。
   **近兩批各發生一次，頻率被低估了，每批都要專門查一遍 hook 的前提。**
   （《Lanquidity》不是「演完 SNL 當晚直奔錄音室」；311 那張的「同名兩張唱片」不存在；
   《Capra Black》查無「Capra 器樂面／Black 人聲面」之分；
   Luiz Bonfá 那批 1959 年錄音**當年就發行過**，不是「2005 年才首度問世」。）
3b. **校對痕跡漏進正文**——特注的否定句被原樣寫進 desc（見「派工的鐵則」），060／061 共 10 處。
   掃描關鍵詞：「卡池」「查無來源」「並非」「而非⋯的重發」「兩者是完全不同」「無從查證」。
3c. **hook 的懸念沒收尾**——hook 立了一個軸（例如「她在婚宴上一場場推翻它」），
   正文卻從頭到尾沒回到那件事。通常是寫作層為壓字數把收尾那句刪掉了。
3d. **來源本身不可靠**——機器驗不出。特別注意：**再發行廠牌自家宣傳頁的最高級宣稱**
   （Bayete 的「Down Beat 年終榜第 1」）、**晚於作品才創設的榜名**
   （1974 年的專輯不可能上 1987 年才有的 Top Contemporary Jazz Albums）。
4. **編制與陣容**——人數、樂器、誰在誰不在。
5. **廠牌與發行年**、**同名作混淆**、**中文音譯人名**、**超譯的最高級**（「史上首度」要有來源）。
6. **跨批矛盾**——單看一批看不出來。（054 與 055 兩張都宣稱疊錄「首度」而後者更早。）

**修正來源錯誤時必須同步改 research／hooks／input 三層**，否則之後會被 `qa-check-research`
誤標成「編造」。hook 改動時 input 的 hook 欄也要同步，且正文首句必須與新 hook 逐字相符。

## 派工的鐵則（血淚換來的）

**特注裡的斷言會被代理當成既定事實往下長。**
凡屬版本鎖定、同名作區分、序號、廠牌歸屬、人物歸屬、分軸軸線的內容，
**一律寫成「請查證」的問句，不要寫成肯定句**，並要求代理「明確列出任何以來源推翻主線的地方」。

改成問句式之後，研究層開始穩定推翻主線假設（近三批共 16 處），
其中包含一次**否決主線的分軸設計本身**（Rahsaan 之名 1970 年才冠上，晚於該作發行，
不能拿來當兩張卡的軸線）。**設計分軸時，軸線本身也要先查證時序。**

**特注裡的否定句會被原封不動寫進消費者看的正文**（060／061 實測 10 處）。
寫「以查證年為準、**不得寫成** 1974 年」，成稿就會出現
「年份有出入：卡池標為 1974 年⋯此處以查證到的 1972 年為準」「卡池標的 1962 年查無來源支撐」
「兩者是完全不同的樂團與作品，僅標題巧合相同」這種**校對痕跡**。
**特注一律改成正面表述**：「正文寫 1972 年」，並加一句
**「這是給你的校對指示，不要在正文交代卡池標錯或版本混淆這件事」**。

其他固定寫進特注的：

- **不動 git repo、不動 PROJECT_MEMORY.md**；臨時腳本一律加批次與組別前綴（`chk-w2-0XX-a.mjs`）。
- **AI 生成的百科站（如 grokipedia）會給錯編制與人名**，單一來源的編制／人名要交叉驗證。
- **回報紀律**：hook 與寫作層不得覆述原文，只回報合格張數＋字數區間＋異常 key 清單。
  （這是內容過濾器中斷的根因，改掉之後已連續多輪零中斷。）
- **字數陷阱**：中文夾大量拉丁人名時字元數遠高於直覺，`Freddie Hubbard` 就吃掉 15 字元。
  爵士／古典／ECM 這類每張要點名四五位樂手的批次，**動筆前就把陣容壓到主故事需要的那幾位**。

## 卡池品質：兩類要主動回報給店主的卡（2026-08-02 裁定）

**這兩類不是簡介寫得好不好的問題，是卡不該存在。查到就別寫，彙整給店主。**

1. **重複卡——同一張唱片有兩張卡**（不同藝人掛名）。
   偵測方式：把預切卡單的專輯名正規化後互比，找出「藝人字串一方包含另一方」的配對。
   全池 2026-08-02 掃出 8 對（《In the Heart of the Moon》甚至有三張卡），已移除 8 張。
   **保留掛名與唱片實際版面一致的那張**（合輯掛名 vs 個人掛名，留合輯）。
2. **無歷史定位的選輯／重發**。
   **光看標題偵測不到**——Mahalia Jackson 有一張就叫《Mahalia Jackson》，是研究層查出才知道是選輯；
   反過來「Gold／Hits／Anthology」字樣的卡多半是正規專輯（Gold Cobra、Solid Gold、Love Over Gold）。
   所以**靠標題掃全池沒有意義，改由研究層在每批逐張確認**（規則已寫進 `prompts/research-base.md`）。
   有定位者保留：完整存檔式現場盒裝、把散落 EP 與單曲首度彙整的權威選輯。

**2026-08-02 店主常設裁定（不必再逐次請示）**：
- **尚未發行的專輯卡 → 一律保留**，走保守寫法（比照 w2-027 的 Bloc Party：寫成已宣布未上市，不編造內容）。
- **雜牌彙編／無歷史定位的選輯與重發 → 一律移除**，直接走下面的移除流程，做完在 progress 與 PROJECT_MEMORY 記一筆即可。

**單曲卡 → 重要的一律保留（店主裁定，2026-08-09 重申並補記）**：
卡片指向的不是專輯而是一支單曲時，**只要那支單曲本身有歷史定位就保留**，
正文照實以單曲的框架書寫（發行形式、廠牌目錄編號、B 面），**絕不要為了湊成專輯而虛構曲目**。
**電子樂特別多這種卡**——house、techno、jungle、dubstep 的關鍵作品有很大一部分只以 12 吋單曲存在，
整個 electronic 家族（w2-113–127）都要按這條處理。
（實例：w2-114 的 `model 500|no ufo's` 是 1985 年 4 月 Metroplex 目錄第一號的 12 吋單曲，查無同名專輯，**保留**。）
沒有歷史定位的單曲才走移除流程。

**移除流程**（沿用 2026-08-01 的前例）：備份 `seed_cards.json` → 移除後**逐筆比對確認只動到目標**
→ 已上線者用 `wrangler kv bulk delete` 同步刪 `desc2:` 鍵 →
**驗證刪除一律走 bulk get API，絕不能用 `/album-desc`**（會觸發重新生成並回寫）
→ 同步清掉預切卡單與該批的 research／hooks／input／output → 重跑 `build-final` 與 `verify-kv`。

## 現行內容規則

- **廠牌（2026-08-02 店主裁定）**：「同一條廠牌敘事只准出現一次」的配額**已取消**。
  **只要該作的背景故事牽涉廠牌就要寫出來**，不必顧慮別張卡是否寫過。
  唯一限制是反同構：不得照貼同一段沿革，每張要從自己這張唱片的角度切進去
  （這是他在該廠牌的第幾張／廠牌當時的處境促成了這張／製作人的哪個決定造就了這張的聲音）。
- **反向禁令兩分法**：晚於發行的事件，**與作品直接綁定者可寫但須標明時序**（成員辭世使本作成為遺作、
  作品的後世流傳、宣傳因某事件中斷）；**與作品無關的後續生平事件一律不寫**（多年後的訴訟、離婚、重組）。
- **題材無禁區**：爭議／逝世／成癮／訴訟是招牌事實，有來源就照寫。僅三限制：要有來源、
  不逐字引歌詞、逝者克制（克制＝不渲染細節，**不是**跳過事實）。
- **字數**：full 卡 180–240（Array.from 計），硬上限 280、下限 140；thin 卡 120–180。
- 詳細的文字規則以 `prompts/*.md` 為準，不要在此重複維護。

## 已知陷阱

- `wrangler` 輸出不要截斷，**要親眼看到 `Success!`**。
- `verify-kv.mjs` 在 Windows 會在印完結果後觸發 libuv assertion，**取結果用 grep，不要用 `tail -1`**。
- 驗證 KV 刪除用 `wrangler kv key get` 看 404，**絕不要用 `/album-desc`**（會觸發重新生成並回寫）。
- 含「..」的 key（`destination... out!`、`some of my best friends are... singers`）
  用 `wrangler kv key get` 會被 Cloudflare 以 403 擋下（路徑穿越保護），**驗證一律走 verify-kv.mjs 的 bulk get**。
- `qa-check-hooks.mjs` 吃批次名，`qa-check-research.mjs` 吃兩個檔案路徑。
- 已知 QA 誤報型：《》內的原文標題被當禁語、綽號夾中間的人名（`Lewis「Flip」Barnes`）被當編造專名、
  專輯名或曲名裡的半形逗號被當中文標點誤用、序數（「第二張專輯」「第二季」）被當榜單名次。
  遇到先查證再決定，不要直接改稿。
- Bash 工具是 POSIX shell，**不要用 PowerShell here-string 寫 commit message**（會多出一個 `@`）。
