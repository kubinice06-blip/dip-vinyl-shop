# 藝人介紹・補洞層共用規則

工作目錄一律 `desc-tools/`（雲端）或 `desc-restyle/`（本機）。**不動任何 git、不動 PROJECT_MEMORY.md。**
臨時檔一律加批名與組別前綴（例：`ar-trial-jazz-g1-tmp.json`），多個代理共用 scratchpad。

## 這一層在做什麼

藝人介紹不再從零研究。每位藝人已經有一份**事實庫**（`batches/artist/facts/<批名>-facts.json`），
裡面是既有專輯研究稿的事實（`research[].facts`，附來源網址）與**已上線的專輯簡介**（`published[].desc`）。
你的工作分三步：

1. **讀事實庫，把能用的事實歸進三格**（2026-09-29 店主改定方向：寫人，不寫履歷）：
   - **`origin` 身世與養成**：出身地、家庭、族群或文化背景、怎麼走上音樂、師承；生卒年或成軍／解散年也放這格。
   - **`sound` 音樂貢獻**：聲音或手法的辨識度、開創了什麼、改變了什麼、在哪個場景或流派源流裡的位置。
   - **`legacy` 影響與地位**：誰受他影響（後輩點名）、跨地域或社會層面的現象、**有出處的共識評價**
     （維基首段的「widely regarded as…」、名人堂、國家級榮譽、權威票選、葬禮或紀念的規模）。
     **這一格是讀者最想知道的，一定要認真查**，但只收有來源的共識，不收單一樂評人的形容詞。
   **人物故事要收細節**（2026-09-30 店主裁定）：若這個人最有名的是一段人生故事（突然消失、轉行、拒絕回歸、身後才被發現），
   把經過的細節逐條收進 `legacy` 或 `era`，每條兩個來源，不要只收一句「後來離開樂壇」的結論。寫作層要靠這些細節把故事寫足。
   另外收 **`era` 輔助年表**（至多 4 條）與 **里程碑**（至多 3 條）：只收真正的轉折與成就，**簽約、轉廠牌、發片日期這類履歷不收**。
2. **判定每一格是 `bank`（事實庫就夠）、`gap`（要補查）還是 `none`（補查後仍查不到）**。
   判準：該格至少要有一條**來源網址完整**的事實，而且足以寫成一句話。
3. **只補查 `gap` 的那幾格**，每位藝人**至多 6 次搜尋**（2026-09-29 由 4 次放寬：試做三輪實測生卒年、成軍年要湊兩個來源常需 5–6 次）。查到就填，查不到就標 `none`，不要硬湊。

**補洞是限量的**：三格（origin／sound／legacy）都是 `bank` 的藝人一次都不要搜。這一層存在的理由就是省下重新研究的成本。

## 事實庫的兩個陷阱（最重要）

### ⚠ 研究稿與上線簡介衝突時，上線簡介為準

人工審稿的更正只修在上線簡介上，**沒有寫回研究稿**。研究稿可能保留已被修掉的錯
（歷史最高頻是「入圍」寫成「得獎」、「某廠牌第一張」、錯的樂手編制）。
從研究稿取一條事實前，先看同一張專輯的 `published[].desc` 有沒有寫到同一件事、寫法是否一致。
**不一致就以上線簡介為準，並把衝突記進 `conflicts`**。上線簡介沒寫到的，研究稿照用。

### ⚠ 專輯研究稿裡的生平是順帶查的

它們是為了寫某張專輯查的，生平只在相關時才出現，而且可能只查到單一來源。
**三類高風險事實必須有兩個獨立來源才收**：生卒年（尤其逝世年）、成員異動年份、「出道作／首張」。
事實庫裡只有一個來源的，列入補查；補查仍只有一個來源的，**不收**。

## 查證規則（沿用 `research-base.md`，重點摘錄）

- 獎項一律寫明**第幾屆／哪一年、類別、入圍還是得獎**；查不到區分就不收。
- 「某廠牌第一張」這類宣稱要反查廠牌沿革，對不上就退成可查證的版本。
- **AI 生成的百科站（grokipedia 等）不得當來源**；只有單一來源的編制、人名、年份要交叉驗證。
- 優先來源：英文或該國語言維基、MusicBrainz、Discogs、AllMusic 藝人頁、官方網站、訃聞（NYT、Guardian 等主流媒體）、
  日本藝人可用日文維基與 CDJournal。
- **`f` 欄只放事實**，查證過程、推翻紀錄、限制說明一律寫進 `notes`。
- **新查的事實（`from: "new"`）一律帶 `src` 與 `src2` 兩個網址（2026-09-30 起，ar-a-008 生效）**：第二源要實際開頁讀到；只看到搜尋摘要的在 notes 註明。
  湊不到第二源的那條移進 notes 並寫「單源」。`qa-artist.mjs gap` 會擋缺 `src2` 的條目。搖滾名人堂官網介紹與引介人致詞例外，可單源進 notes，開頭寫「名人堂官方（可具名單源）」。
- **notes 裡記了「來源不一致」的值，facts 就不得帶那個值**（試做批 Uno Naissoo 的 Swing Club 年份：notes 寫了兩源不一致，facts 仍放進其中一個年份，寫作層照寫，靠主線審稿才拿掉）。

## 輸出格式

`batches/artist/research/<批名>-g<組號>.json`，陣列，每位一筆：

```json
{
  "key": "lee morgan",
  "name": "Lee Morgan",
  "slots": {
    "origin": { "status": "bank", "facts": [ { "f": "…", "src": "https://…", "from": "bank" } ] },
    "sound":  { "status": "gap",  "facts": [ { "f": "…", "src": "https://…", "src2": "https://…", "from": "new" } ] },
    "legacy": { "status": "gap",  "facts": [ … ] },
    "era":    { "status": "bank", "facts": [ … ] }
  },
  "milestones": [ { "f": "…", "src": "https://…", "from": "bank" } ],
  "conflicts": [ "研究稿 c135-a 說⋯；上線簡介寫⋯；採上線簡介" ],
  "searches": 2,
  "status": "full",
  "notes": "…"
}
```

- `from`：`bank`＝取自事實庫（`src` 照抄事實庫該條的網址）、`new`＝本層補查。
- `status`：origin、sound、legacy 三格都有料為 `full`；只撐得起身世與聲音、地位查不到的為 `thin`。`era` 是輔助格，可以是 `none`。
- `searches`：本位實際用掉的搜尋次數（WebSearch 與 WebFetch 合計）。三格全 `bank` 應為 0。
  **取不到內容的請求（403、404、503、付費牆）不計入上限**（2026-09-30 裁定：上限是為了控成本，失敗請求幾乎不花 token；
  把它算進去會讓重要藝人因為一兩個壞連結少查兩次）。另記在 `failedFetches`，上限 4 次。
- `pubIssues`（2026-09-30 量產起）：查證時發現**已上線專輯簡介**寫錯或過時的地方，逐條
  `{ "album": "…", "claim": "上線簡介原句重點", "problem": "問題與依據", "src": "https://…" }`。沒有就給空陣列。
  這份清單交店主在本機改 KV；`conflicts` 只記「本層怎麼裁定」，`pubIssues` 只記「上線簡介要改什麼」，兩邊可以重複。

## 同名不同人（量產必看）

名冊只認字串。動手前先看事實庫的 `poolAlbums`（卡池裡這個名字的全部專輯），**確認你查的是發這些專輯的那個人／團**。
同名的另一個人（例如同名的古典與流行樂手、同名的不同國家樂團）一條都不要收。
若卡池專輯顯示這個名字底下其實混了兩個不同的人，在 `notes` 開頭寫「⚠ 同名混卡：…」，只寫專輯數多的那一位。

## 紀律

- **每做完 3 位就把目前結果寫進輸出檔**（容器會不定時重啟）；若輸出檔已有部分內容，**讀進來接續補完，不要從頭重寫**。
- 回報只寫：完成幾位、各位的三格狀態與搜尋次數、推翻事實庫之處、查不到的格。**不要覆述事實原文。**
